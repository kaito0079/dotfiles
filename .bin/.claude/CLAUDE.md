# 共通ルール（ユーザー横断）

リポジトリを問わず適用する Claude への指示。プロジェクト固有の規約は各リポジトリの `CLAUDE.md` に書く。

## コミュニケーション

- チャット応答では丸数字（①②③）を使わない。読みづらいため、番号付きリスト（1. 2. 3.）等を使う。資料・ドキュメントを作成するときは必要に応じて使用してよい。
- 実現可否・コスト・時間に関する質問には、まず 1 段落で簡潔に回答する。指示がない限りコードベースの長時間探索を開始しない。深掘りが必要なら、何を調べるかを提示してから着手する。
- 設計・規約に踏み込む推奨をする場合は、コードまたはドキュメントの具体的な根拠を示す。「業界標準」「ベストプラクティス」だけを根拠にしない。
- 憶測で断定しない。コードベース・スキーマ・環境・ツールの挙動・仕様など事実に関する主張は、現物や一次情報を確認してから書く。確認手段があるならまず確認する。確認できない場合のみ「未確認だが」「〜のはず」など推測である旨を明示する。存在しないカラム名・関数・環境を推測で当てない。
- 憶測を前提に実装・修正・回答を進めない。推測のまま進めると確認の往復が増えるため、不確かな点は確認してから着手するか、推測である旨を明示して確認を求める。
- アーキテクチャや方針に関わる依頼は、最初のメッセージで制約・前提を確認し、合意してから実装に入る。

## 実装方針

- 要求されていないカラム・機能・防御策や、過剰に複雑なクエリを先回りで追加しない。まずシンプルな案から始め、拡張は必要になった時点で提案する。
- 完了報告の前に lint・テスト等の検証コマンドを実行する。実行していない場合は、完了報告にその旨を明示する。
- ツールのインストールや環境変更を伴う作業は、着手前に必要性を伝えて確認を取る。
- 依頼されていない成果物（HTML・ドキュメント・サマリファイル等）や無関係な変更（リファクタリング・lockfile の変動等）は、作成・commit する前に必要性を伝えて確認を取る。

## Git / ブランチ衛生

- 編集前に `git branch --show-current` を確認する。意図しないブランチ自動切り替えはしない。
- PR 用ブランチを作成するときは base ブランチを確認する。main 起点と決めつけず、積み上げ先のブランチがある場合はそこから切る。
- PR 修正タスクでは、関連する `fix/*` ブランチが既に存在するかを最初に確認し、二重作業を避ける。
- 通常のコミットでは、メッセージに `Co-Authored-By` 行や 🤖 等の Claude クレジット表記は付けない。ただし commit-helper のような専用スキル経由でコミットする場合は、そのスキルの規約に従う（クレジット行の付与を妨げない）。

## PR レビュー

- レビュー実行前に、対象の diff のファイル数を `gh pr view <N> --json changedFiles` と照合する。PR の変更ファイル数を超える diff（例: main...HEAD で他 PR の変更を含むもの）をレビューしない。超過が判明したら停止してスコープを確認する。
- レビュー指摘に憶測を含めない。リモート HEAD の実コードで file:line まで確認できたもののみを指摘として報告する。調査しきれず可能性が残る事項は、指摘とは分けて「未検証の懸念」として報告し、コメント投稿の対象にしない。
- コメント投稿・レビュー submit・push などの外部公開操作はサブエージェントに委譲しない。親セッションがユーザーの確認を得てから実行する。
- レビュー専任タスクではコードを直接編集しない。指摘はレビューコメントとして記録し、修正はユーザーの依頼があってから行う。
- 既存プロジェクトの慣例・パターンに合致する指摘は省略するか重要度を下げる。
- 問題が複数行にまたがる場合は単一行ではなく複数行レンジで指摘する。
- インラインコメントはまず PENDING で投稿し、ユーザー確認後に APPROVED / REQUEST_CHANGES を提出する。
- 重要度の校正基準が曖昧なときは、投稿前にサマリ表を提示して合意を取る。
- PENDING のレビューコメントは REST の PATCH では更新できない（404 になる）。GraphQL の `updatePullRequestReviewComment` を使う。
